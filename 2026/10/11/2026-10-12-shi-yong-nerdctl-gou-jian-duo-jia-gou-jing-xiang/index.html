我的实际环境是一个 Kubernetes WebIDE Pod：容器中没有 systemd，也没有 CAP_SYS_ADMIN。虽然可以把 Docker 静态二进制安装到 /usr/local/bin，甚至让 dockerd 使用 vfs 存储驱动启动，但拉取镜像时仍会在解包镜像层阶段失败：

原因是当前 Pod 不能创建 mount namespace。在这个环境里继续切换 Docker 存储驱动、安装 iptables，或者把命令从 Docker 换成 Nerdctl，都无法补回缺失的内核权限。

因此，本文采用客户端与构建端分离的方式：

  1. 在 WebIDE Pod 中只安装 buildctl v0.14.1，用于提交构建任务。
  2. 在具备 CAP_SYS_ADMIN、containerd 和 systemd 的构建节点上运行 buildkitd。
  3. QEMU 和 binfmt_misc 也配置在构建节点，而不是 WebIDE Pod。
  4. 构建结果由 BuildKit 直接推送到 Registry，WebIDE 中不执行本地 docker pull 或 nerdctl run。

本文以 linux/amd64 和 linux/arm64 为例，记录这套适用于非特权开发容器的多架构构建流程。

本文参考了陈少文的《使用 Nerdctl 构建多架构镜像》，并结合实际使用重新组织和补充。

多架构镜像是什么

多架构镜像并不是一份二进制同时兼容 x86 和 ARM，而是一个 OCI Image Index 指向多份不同平台的子镜像：

使用者拉取统一标签时，容器运行时会根据宿主机平台选择对应的镜像。这样，部署清单不需要分别维护 hello-amd64 和 hello-arm64 两个地址。

这里的 WebIDE Pod 只运行 BuildKit 客户端。BuildKit daemon、containerd 以及跨架构执行所需的 QEMU 和 Linux binfmt_misc 全部位于远端构建节点。

几个变量的含义如下：

  • BUILDPLATFORM：实际运行构建任务的主机平台。
  • TARGETPLATFORM：当前输出镜像的完整目标平台，如 linux/arm64。
  • TARGETOS：目标操作系统，如 linux。
  • TARGETARCH：目标 CPU 架构，如 amd64 或 arm64。
  • TARGETVARIANT：架构变体，如 ARM 的 v7，也可能为空。

下载地址的命名方式并没有统一标准。有些项目使用 x86_64、aarch64，另一些使用 amd64、arm64，不能直接假设 ${TARGETARCH} 一定与上游文件名一致。必要时应在 Dockerfile 中建立显式映射。

常见问题

提示 exec format error

通常有三种原因：

  1. QEMU 或 binfmt_misc 没有正确注册。
  2. 下载的业务二进制与 ${TARGETARCH} 不匹配。
  3. 镜像索引中的平台标注与镜像真实内容不一致。

Docker pull 仍然报 ApplyLayer 错误

这正是当前非特权 Pod 的环境限制。下面这些调整不能从根本上解决问题：

  • 将 Docker 存储驱动从 overlay2 改成 vfs。
  • 安装 iptables 并重新启动 dockerd。
  • 添加 --iptables=false --bridge=none。
  • 使用 Nerdctl 代替 Docker CLI。

解决方式是给 Pod 增加构建所需的 capability 并按安全规范运行特权构建容器，或者像本文一样把构建和镜像运行放到外部节点。若目的只是复制镜像而不是运行，也可以使用 Skopeo 在 Registry 与 OCI archive 之间复制，因为它不需要把镜像解包进本地容器文件系统。

Kubernetes 中看不到刚构建的镜像

containerd 使用 namespace 隔离资源。Kubernetes 常用 k8s.io，Nerdctl 默认 namespace 则可能不同。可以显式指定：

不过，多架构镜像的可靠交付方式仍然是推送到 Registry，再由各节点按 digest 或统一标签拉取，而不是依赖某台机器的本地 namespace。

跨架构构建为什么很慢

QEMU 需要翻译 CPU 指令，包含大量编译工作的 RUN 阶段会明显变慢。可以采用以下优化方式：

  • 使用原生 amd64 和 arm64 构建节点并行构建。
  • 把编译阶段固定在 $BUILDPLATFORM，通过交叉编译输出目标架构程序。
  • 合理使用 BuildKit cache mount 和远端缓存。
  • 将依赖下载与业务编译拆分，减少无效缓存失效。

总结

当前环境下的关键链路是：

在无 systemd、无 CAP_SYS_ADMIN 的 WebIDE Pod 中，能够启动 Docker daemon 不等于能够拉取或运行镜像。将 buildctl 客户端与有权限的远端 BuildKit 分离，既绕开了本地 mount namespace 限制，也避免为了构建镜像而把开发 Pod 直接改成特权容器。最后仍需检查远端镜像索引，并在原生 amd64、arm64 节点上完成冒烟测试。
